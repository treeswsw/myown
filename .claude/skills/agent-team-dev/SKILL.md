# 에이전트 팀 개발 방식

사용자와 함께 기획하고, 여러 에이전트에게 나눠 만들고, 검토·확인을 거쳐 배포하는 절차다.
목표는 세 가지다. ① 다시 만드는 일을 없앤다 ② 기다리는 시간을 줄인다 ③ 확인하지 않은 것을 확인했다고 말하지 않는다.

프로젝트에 CLAUDE.md가 있으면 구역 지도·검증 명령·브랜치 규칙은 그쪽을 따른다.
없으면 이 스킬의 4단계에서 만들어 저장소에 넣는다.

## 1. 역할과 모델

| 역할 | 모델 | 하는 일 | 하지 않는 일 |
|---|---|---|---|
| 관리자(메인 대화) | Fable 권장 | 기획 확정, 과제 분배, 병합, 최종 확인, 사용자 보고 | 코드 작성, 느린 시각 확인 |
| 작업자 | Sonnet | 코드와 시험 작성 | 구역 밖 파일 수정, 푸시 |
| 검토자 | Opus | 과제별 변경분 검토 | 직접 수정, 취향으로 막기 |
| 최종 확인 | Fable | 요청 항목과 결과 대조, 확인 등급 부여 | 코드 재검토 반복 |
| 단순 작업 | Haiku | 이름 바꾸기, 문구 수정 같은 기계적 변경 | 판단이 필요한 일 |

- 메인 대화가 Fable이 아니면 기획 결정과 최종 확인은 Fable 서브에이전트에게 맡긴다.
- 검토자는 "코드가 맞는가"를, 최종 확인은 "사용자가 요청한 것이 됐는가"를 본다. 서로 겹치지 않게 한다.
- 디자인 감각이 필요한 것(특수 연출, 첫 화면 시안)은 Fable 서브에이전트에게 준다.
- 메인 대화의 맥락이 70%를 넘으면 사용자에게 새 대화를 권한다. 규칙은 CLAUDE.md와 기획 문서에
  남아 있어야 하므로, 결정 사항은 그때그때 문서에 적는다.

## 2. 기획: 코드보다 먼저

### 2-1. 시안 먼저
- 화면이 있는 것은 정적인 시안(가짜 데이터, 한 화면씩)을 먼저 보여주고 확정받는다.
- 시안 단계에서 정하는 것: 화면 목록, 각 화면의 요소와 위치, 주요 상태(비었을 때, 오류, 내 차례 등).
- 시안이 확정되기 전에는 서버·화면 코드를 시작하지 않는다.

### 2-2. 규칙 체크리스트
아래 질문에 답을 받아 기획 문서(docs/SPEC.md 등)에 적는다. 해당 없는 항목은 "해당 없음"이라 적는다.

1. 누가 쓰는가? 동시에 몇 명인가? 로그인은 어떻게 하는가?
2. 무엇을 저장하는가? 어디에 저장하고 초기화는 어떻게 하는가?
3. 핵심 흐름은 무엇인가? 시작부터 끝까지 단계별로.
4. 각 단계의 끝 조건은? 시간제한이 있는가? 넘기면 어떻게 되는가?
5. 중간에 나가거나 연결이 끊기면? 다시 들어오면?
6. 점수·돈·재화가 있다면 어디에 있고, 0이 되면 어떻게 되는가?
7. 결과는 어떻게 보여주는가? 몇 초 동안? 건너뛸 수 있는가?
8. 여러 사람이 함께 쓴다면 어떻게 만나는가(목록, 코드, 초대)? 주인 권한은?
9. 예외 상황(동점, 동시 입력, 잘못된 입력, 악용)은 어떻게 처리하는가?
10. 어느 기기와 브라우저를 지원하는가? 터치 조작은?
11. 소리와 움직임이 있는가? 끌 수 있는가?
12. 어디에 배포하는가? 비용 제한은? 어느 브랜치가 배포되는가?
13. "이러면 완성"이라고 할 확인 시나리오 3~5개는 무엇인가?

- 사용자가 정하지 않은 항목은 관리자가 기본값을 제안하고 "이대로"를 받는다.
- 13번 시나리오는 그대로 자동 시험이 된다.
- 만든 뒤에 규칙을 바꾸는 요청이 오면: 기획 문서를 먼저 고치고, 영향받는 곳(서버, 화면, 시험)을
  사용자에게 한 줄로 알린 뒤, 서버 → 시험 → 화면 순서로 반영한다.

## 3. 뼈대와 빠른 확인 수단을 먼저 만든다

기능 과제를 나누기 전에 아래를 먼저 갖춘다. 이것이 없으면 병렬 작업의 결과를 믿을 수 없다.

- 빠른 확인 명령 하나(예: `npm run check`). 빌드 + 단위 시험 + 클릭 스모크를 1분 안에 끝낸다.
- 클릭 스모크 시험: 실제 서버에 실제 앱을 띄우고 브라우저로 실제 클릭을 해서 핵심 흐름을 한 번 돈다.
  판정은 서버가 받은 내용이나 화면의 글자로 한다. 그림 비교는 쓰지 않는다.
- 가림 검사: 주요 상태마다 보이는 모든 버튼의 중심점에서 실제로 그 버튼이 눌리는지 확인한다.
- 무거운 그래픽(3D, 영상)이 있으면 그것을 끄는 시험용 모드를 만든다. GPU가 없는 환경에서도
  화면 조작 시험이 몇 초 안에 끝나야 한다.
- CSS 규칙: 모듈마다 클래스 접두사, 전역 클래스는 한 파일에만, 넓은 선택자로 동작을 바꾸지 않는다.
  가능하면 이 규칙을 검사하는 시험을 둔다.
- 화면 구석에 버전(커밋 번호)을 표시한다. 사용자가 어느 판을 보고 있는지 알 수 있어야 한다.

## 4. 구역 지도

- 저장소를 구역으로 나눠 CLAUDE.md에 적는다. 구역 = 한 에이전트가 혼자 고쳐도 되는 파일 묶음.
- 여러 구역이 함께 쓰는 파일(진입 파일, 전역 스타일, 공용 도구, 설정, 문서)은 "통합 구역"으로 묶고
  한 번에 한 에이전트만 고친다.
- 구역 사이의 약속(통신 메시지, 함수 모양, 데이터 형식)은 관리자가 기획 문서에 먼저 적는다.
  그래야 양쪽을 동시에 만들 수 있다.

예시(실시간 게임 사이트): 서버 / 로비 / 채팅 / 게임 UI / 3D·연출 / UI 시험 / 통합.

## 5. 분배

- 과제 1개 = 새 에이전트 1개 = 구역 1개. 항목 3개 이하, 20분 이내 분량으로 자른다.
- 한 에이전트에게 계속 일을 얹지 않는다. 맥락이 쌓일수록 느려지고 틀린다.
- 코드를 쓰는 에이전트는 모두 워크트리 격리로 띄운다. 자기 브랜치에 커밋만 하고 푸시하지 않는다.
- 서로 다른 구역의 과제는 동시에 띄운다. 같은 구역의 과제는 차례로 한다.
- 통합 구역 변경이 필요한 작업자는 직접 고치지 않고 "어느 파일에 무엇을"을 반환 보고에 적는다.
  병합 뒤 통합 담당 에이전트 하나가 모아서 반영한다.
- 공용 게시판 문서는 관리자만 쓴다(병합 충돌 방지).

과제 지시문에 반드시 넣을 것:
1. 무엇을, 왜(사용자가 한 말 그대로 포함)
2. 고쳐도 되는 파일과 고치면 안 되는 파일
3. 지켜야 할 약속(기획 문서의 해당 절)
4. 끝났다는 증거(통과해야 할 명령, 추가할 시험)
5. 하지 말 것(느린 시각 확인, 범위 밖 정리, 푸시)
6. 반환 형식: 바꾼 것 / 확인한 것과 등급 / 못 한 것 / 통합 구역에 필요한 변경

### 작업 중에 새 요청이 오면
- 실행 중인 에이전트에게 덧붙이지 않는다(메시지는 늦게 도착하고 맥락만 늘어난다).
- 그 구역이 비어 있으면 새 에이전트를 바로 띄운다.
- 그 구역이 작업 중이면 대기열에 적고, 반환된 뒤 새 에이전트에게 준다.
- 진행 중인 작업을 무효로 만드는 요청이면 그 에이전트를 중단하고 새 지시문으로 다시 띄운다.
- 접수할 때마다 사용자에게 한 줄로 알린다: "접수, 어느 구역, 언제쯤".

### 버그 신고 묶음(3~6건)의 표준 처리
1. 5분 안에 구역별로 나눈다. 원인이 불분명한 것은 조사 전용 에이전트(읽기만)에게 먼저 준다.
2. 구역별 작업자 2~4개를 동시에 띄운다.
3. 반환되는 대로 검토 → 병합 → 빠른 확인.
4. 전부 모이면 최종 확인 후 배포하고 보고한다.

## 6. 검토와 병합

1. 작업자 반환 → 검토자(Opus)가 그 브랜치의 변경분만 본다.
2. 검토 기준: 버그, 기획 문서와 다른 동작, 구역·CSS·약속 위반, 시험 없는 새 동작.
   이것만 병합을 막는다. 그 밖의 의견은 대기열로 보낸다.
3. 막힌 과제는 지적 사항과 함께 새 작업자에게 준다(같은 에이전트는 한 번까지만 이어 쓴다).
4. 통과한 과제는 관리자가 개발 브랜치에 병합하고 빠른 확인 명령을 돌린다.
5. 충돌이나 확인 실패는 관리자가 직접 고치지 않고 새 작업자에게 넘긴다.
6. 검토자는 묶음마다 새로 띄운다.

## 7. 검증 규칙

- 병합 조건은 빠른 확인 명령 통과다. 느린 전체 시험은 그 부분을 바꾼 과제와 배포 직전에만 돌린다.
- 화면 과제는 실제 앱에서 실제 클릭으로 확인한다. 따로 만든 데모 페이지나 가짜 데이터만으로
  완료라 하지 않는다. 전역 스타일 충돌은 실제 앱에서만 드러난다.
- 새 버튼이나 화면을 만들면 클릭 스모크에 한 줄을 추가한다.
- 느린 확인(그래픽 스크린샷, 여러 화면 크기 순회)은 사용자가 요청할 때만 한다.
- 이 환경에서 확인할 수 없는 것(실제 기기, 특정 브라우저, 소리, 움직임의 느낌)은 확인을 시도하지
  않고 사용자에게 확인을 부탁한다.

모든 보고에 확인 등급을 붙인다. 이 네 가지 밖의 "확인됨"은 쓰지 않는다.
- ① 자동 시험 통과
- ② 실제 서버에서 실제 클릭으로 확인
- ③ 가짜 데이터 화면에서만 확인
- ④ 미확인 (사용자의 실기기 확인 필요)

## 8. 배포

- 개발 브랜치와 배포 브랜치를 나눈다. 배포 브랜치에 자동 배포가 걸려 있으면 개발 브랜치는
  배포되지 않아야 한다. 나뉘어 있지 않으면 사용자에게 먼저 나누자고 제안한다.
- 개발 브랜치: 병합된 과제마다 푸시한다. 항상 빠른 확인을 통과하는 상태로 둔다.
  미완성은 워크트리 브랜치에 둔다. "작업 중" 커밋을 넣지 않는다.
- 배포 브랜치: 묶음이 검토·빠른 확인·전체 시험·최종 확인을 모두 통과했을 때만 올린다.
  강제 푸시와 직접 커밋은 하지 않는다.
- 배포가 사용 중인 사람을 끊는다면(서버 재시작 등) 올리기 전에 사용자에게 묻는다.
- 허락받지 않은 브랜치나 설정은 건드리지 않는다. 필요하면 무엇을 왜 바꾸려는지 말하고 허락을 받는다.

## 9. 최종 확인

배포 직전에 한 번 한다.
1. 사용자가 요청한 항목을 목록으로 만든다(말한 그대로).
2. 항목마다 병합된 변경에서 해당 부분을 찾아 "됨 / 일부 / 안 됨"을 적는다.
3. 빠른 확인과 전체 시험 결과를 직접 본다(작업자의 보고를 그대로 믿지 않는다).
4. 항목마다 확인 등급을 붙이고, ③④ 등급은 사용자가 직접 볼 것을 구체적으로 적는다.
5. "안 됨"이 있으면 배포하지 않거나, 그 항목을 빼고 배포한다고 분명히 알린다.

## 10. 사용자 보고

- 쉬운 말로, 짧게 쓴다. 파일 이름과 내부 용어 대신 사용자가 보는 화면의 말로 쓴다.
- 접수 즉시: 몇 건인지, 어떻게 나눴는지, 예상 시간.
- 진행 중: 끝난 것만 한 줄씩. 진행률을 추측해서 말하지 않는다.
- 배포 시 항목별로:
  - 무엇을 고쳤는지
  - 확인 등급
  - 직접 확인할 것(어느 기기에서 무엇을 눌러 볼지)
  - 버전(커밋 번호)
- 하지 못한 것과 확인하지 못한 것을 가장 먼저 적는다.
- 아직 배포 브랜치에 올리지 않은 것은 "개발 브랜치에만 있음"이라고 적는다.

## 11. 흔한 실패와 막는 규칙

| 실패 | 막는 규칙 |
|---|---|
| 한 에이전트에게 일이 몰려 한 번에 한 시간씩 걸림 | 과제 1개 = 새 에이전트 1개, 20분 분량 (5절) |
| 만든 뒤 규칙이 바뀌어 서버·화면·시험을 다시 씀 | 규칙 체크리스트를 코드보다 먼저 (2절) |
| 버튼이 실제 사이트에서 안 눌림 | 클릭 스모크와 가림 검사가 병합 조건 (3, 7절) |
| 부품은 멀쩡한데 합치면 깨짐 | 실제 앱에서 확인, CSS 접두사 (3, 7절) |
