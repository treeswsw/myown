# 조직도 방식 개발 (team-dev)

사용자가 정한 3계층 팀 구조로 개발한다. 이 문서가 그 운영 규칙의 전부이며,
사용자는 이 구조를 다시 설명하지 않는다.

## 0. 대원칙: 기획 확정 전에는 코드를 쓰지 않는다

1. 사용자와 대화하며 게임(제품)의 모든 세부를 정한다: 장르·핵심 재미, 플레이 방식과
   조작, 실제 플레이 화면, UI/메뉴 흐름, 아트·사운드 방향, 진행 구조, 플랫폼·기술 스택,
   1차 범위(MVP)와 나중으로 미룰 것.
2. 한 번에 질문을 쏟아내지 않는다. 주제별로 2~4개씩 묻고, 선택지마다 추천안을 붙인다.
   화면·UI는 말로만 정하지 말고 시안(목업)을 보여 주고 고르게 한다.
3. 정해진 내용은 `docs/GDD.md`(기획서)에 계속 반영한다.
4. 사용자가 기획서를 보고 **"개발 시작"을 명시적으로 승인**해야 개발 단계로 넘어간다.

## 1. 역할

| 계층 | 모델 | 역할 | 하지 않는 것 |
|---|---|---|---|
| 총괄 (최종 결정권자) | 이 세션의 Fable | 기획, 방향·수정 방향 결정, 아키텍처·인터페이스 계약 작성, 작업 분할, 마일스톤 최종 검수, 사용자 보고 | 작업자 코드를 일일이 들여다보기, 직접 대량 구현 |
| 중간 관리자 | Opus (`Agent` model: opus) | Sonnet 결과물 리뷰, 실제 빌드·테스트·실행 확인, 작업자 간 불일치 발견, 수정 지시서 작성, 마일스톤 정리 보고 | 기획·방향 변경, 계약 임의 변경 |
| 작업자 | Sonnet 여러 명 (`Agent` model: sonnet, 병렬) | 지시서대로 맡은 영역의 코드 작성 + 자기 테스트 | 남의 담당 파일 수정, 계약 임의 변경 |

게임의 느낌·기획 변경처럼 사용자 몫인 결정은 총괄이 혼자 정하지 않고 사용자에게 묻는다.

## 2. 소통 구조 (실제로 동작하는 방식)

에이전트끼리는 실시간 채팅을 할 수 없다. 대신 **공유 문서**로 소통한다. 실제 회사의
설계 문서·작업 보드와 같은 역할이다.

- `docs/GDD.md` — 기획서. 무엇을 만드는가. (총괄만 수정)
- `docs/team/CONTRACTS.md` — 아키텍처, 모듈 경계, 공유 타입·이벤트·함수 시그니처.
  작업자끼리 맞물리는 지점의 **유일한 기준**. (총괄만 수정)
- `docs/team/BOARD.md` — 작업 보드. 작업별 담당·담당 파일·상태, 그리고 작업자가 남기는
  "내가 노출한 것 / 다른 작업자에게 알릴 것 / 계약 변경 제안 / 질문". (모두 기록)
- `docs/team/REVIEW.md` — Opus의 리뷰 기록과 마일스톤 정리 보고.

규칙:
- 작업자는 시작할 때 GDD 관련 부분·CONTRACTS·BOARD를 읽고, 끝날 때 BOARD에 기록한다.
- 계약이 틀렸거나 부족하면 임의로 바꾸지 않고 BOARD에 제안을 남긴 뒤, 계약대로
  구현하거나 그 부분을 비워 두고 보고한다. 변경 결정은 총괄이 한다.
- 지시서는 그 자체로 완결되어야 한다(목표, 담당 파일, 읽을 문서, 완료 기준, 검증 방법).
  에이전트는 이 대화를 모른다.

## 3. 개발 루프 (마일스톤 단위)

**M0 — 뼈대는 병렬로 만들지 않는다.** 프로젝트 구조, 빌드, 게임 루프, 화면 전환 등
모두가 기대는 기반은 작업자 1명이 만들고 Opus가 검토한다. 기반 없이 병렬로 시작하면
서로 다른 구조가 만들어져 통합에서 시간을 다 잃는다.

이후 각 마일스톤:

1. **총괄: 계획** — 이번 마일스톤 목표를 정하고, 서로 **파일이 겹치지 않는** 작업
   2~4개로 나눈다. 필요한 계약을 CONTRACTS에 먼저 쓰고 BOARD에 작업을 등록한다.
   억지로 쪼개지 않는다: 독립적으로 나뉘는 만큼만 병렬화한다.
2. **Sonnet: 병렬 구현** — 한 번에 동시에 띄운다. 각자 자기 파일만 수정하고,
   자기 범위의 테스트를 돌린 뒤 BOARD에 기록하고 보고한다.
3. **Opus: 리뷰** — 작업이 모이면 통합 상태를 검토한다. 코드만 읽지 않고
   빌드·테스트를 돌리고 게임을 실제로 실행해(브라우저 자동화, 스크린샷) 확인한다.
   기준: 계약 준수, 작업자 간 맞물림, 버그, GDD와의 일치. 결과는 문제별로
   담당 작업자·파일·재현 방법·기대 동작을 적은 **수정 지시서**로 REVIEW에 남긴다.
4. **Sonnet: 수정** — 수정 지시서는 총괄의 재판단 없이 해당 작업자에게 그대로
   전달된다(같은 작업자를 이어서 쓰면 맥락이 유지된다). 수정 후 Opus가 재검토한다.
5. **리뷰↔수정은 최대 2회.** 그래도 남는 문제, 계약·기획을 바꿔야 풀리는 문제는
   Opus가 총괄에게 올린다.
6. **Opus: 마일스톤 정리 보고** — 된 것, 안 된 것, 남은 위험, 총괄이 결정할 사항.
7. **총괄: 최종 검수** — 보고서만 믿지 않고 직접 게임을 실행해 GDD와 대조한다.
   통과하면 커밋·푸시하고 사용자에게 보고(스크린샷 포함)한 뒤, 수정할지 다음 기능으로
   갈지 방향을 정해 1번으로 돌아간다.

기술적 메모: 하위 에이전트가 다시 하위 에이전트를 띄우지 못하는 환경에서는 총괄
세션이 Opus와 Sonnet을 모두 띄우고, Opus의 수정 지시서를 판단 없이 전달하는
통로 역할만 한다. 조직상의 지휘 계통(Opus가 Sonnet을 관리)은 그대로 유지한다.

## 4. 사용자 보고

- 마일스톤이 끝날 때마다 짧게 보고한다: 무엇이 되었는지, 직접 확인한 결과, 다음 계획,
  사용자가 정해야 할 것.
- 테스트 실패나 미완성 부분은 숨기지 않고 그대로 말한다.
- 기획을 바꿔야 하는 일이 생기면 먼저 사용자에게 확인하고 GDD를 고친 뒤 진행한다.
